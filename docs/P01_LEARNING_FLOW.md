# P01 — 과제 수행과 근거 중심 피드백

## 제품 흐름

개발 취업 준비생이 AI와 과제를 수행하고 선택·검증 과정을 돌아보는 훈련이다.
분석 보고서와 구현 과제에 공통으로 **과제 이해 → AI와 작업 → 내 결과물 검증 → 제출 → 직접 설명 → 피드백 → AI와 재연습**을 적용한다.
총점·종합 등급·합격 예측·독립적인 실력 인증은 제공하지 않는다.

훈련은 사용자가 선택하는 3개 힌트를 제공한다. 모의 전형은 같은 목표·제약·평가 기준과 작업 AI를 제공하고 힌트 API/버튼은 차단한다. 힌트 사용을 감점하지 않고 피드백에 맥락으로 전달한다. 강제 시간제한·감독 기능은 없다.

P01 구현 당시 새 진입점은 `/learn`이며 `/`도 이곳으로 이동했다. 현재는 `/`가 공개 랜딩, `/learn`이 로그인 후 내 학습 화면이다. `/tasks`는 보고서·구현 과제를 함께 보여 주는 공개 카탈로그이며 독립 `구현 연습` 메뉴는 표시하지 않는다. 기존 `/sessions/{id}`, `/coding`, `/coding/{id}` URL은 저장 흐름 호환을 위해 보존한다. 새 과제의 대표 화면은 `/learn/{id}`이며 별도 검산 초안을 필수로 거치지 않는다. 환경 확인은 `/environment`다.

## 대표 과제 v1

### 결제 지연 상황을 동료에게 설명하기

가상 운영 담당자로서 10:00~10:10 결제 API 지연 관측 기록을 읽는다. 시간·지연·오류율·CPU·메모리와 **아직 수집하지 못한 지표**를 함께 제공한다. 사실과 추정, 원인 미확인 상태를 구분하고 다음 확인/대응 방법을 동료에게 전달하는 보고서를 작성한다.

제출물은 보고서, 선택한 자료 줄 인용, 채택 이유와 검증 설명이다. 인용을 클릭했다는 사실만으로 원본 대조 능력을 확정하지 않는다. 검증하지 못했으면 그 사실을 쓸 수 있다. 직접 설명 두 번째 질문은 다른 API에서도 지연이 관찰됐다는 조건에서 재검토할 가설과 대응이다. 새 조건에 대한 답변만으로 실제 개선을 수행했다고 판정하지 않는다.

공개 가상 자료는 local 프로필의 V17에 신규 과제 UUID/버전으로 제공한다. 이전 browse-demo 및 private task-pack은 수정하지 않았다. 내용은 개발자가 작성한 대표 시나리오이며 독립적인 전문가 콘텐츠 검수 완료를 뜻하지 않는다. production 프로필에서 자동 발행하지 않는다.

### 중복 없이 항목 추가하기

`addItem(items,item)`의 중복 id 처리·순서·입력 보존을 확인한다. 기존 JavaScript 단일 파일/QuickJS 실행기를 재사용한다. 완성된 코드 요청도 허용하며 직접 작성량·대화 횟수로 평가하지 않는다. 공개 테스트 실패 상태에서도 현재 버전의 테스트 기록과 설명이 있으면 제출할 수 있다.

직접 설명 두 번째 질문은 동일 id의 title 갱신이라는 요구 변경에 맞춰 수정/검증할 부분이다. 브라우저 테스트는 클라이언트가 보고한 공개 연습 기록으로 표시하며 독립 서버 채점·보안 인증·역량 점수로 승격하지 않는다. 여러 파일·언어·패키지 실행·서버 비공개 채점은 추가하지 않았다.

## 기록과 평가 경계

V16의 learning_flows는 기존 보고서 session 또는 coding workspace 중 하나를 연결한다. 흐름 버전은 `learning-flow-v1`, 모드는 생성 시 고정한다. 기존 저장 모델을 통째로 바꾸거나 기존 제출본을 마이그레이션하지 않는다.

- 생성 요청 key로 중복 작업 생성을 막고 사용자당 최대 50개를 둔다. 재연습은 원본당 한 개 자식 작업을 만들며 같은 요청의 재실행은 같은 자식을 반환한다. 재연습의 재제출 후 다시 재연습할 수 있다.
- 설명·인용 저장은 flow version CAS. 결과물 제출은 화면에 표시된 artifact version/hash로 확인한다. 진행 중 AI 응답과 미저장 변경이 있으면 제출하지 않는다.
- 저장·테스트 이벤트를 결과물과 같은 트랜잭션에서 기록한다. 제출 시 완료 대화, 공개 자료, 제출 설명·인용, 이벤트, 힌트, 결과물을 고정한다. 검산 정답과 조건 미공개 자료는 입력에 넣지 않는다.
- 보고서의 인용 범위는 같은 과제의 공개 자료로 서버가 검증하고 원문을 추출한다. 새로운 흐름에 속한 작업은 이전 단독 제출 API로 우회 제출할 수 없다.
- 제출 스냅샷과 직접 설명, 발행 피드백은 DB 트리거로 덮어쓰기를 차단한다. 상태는 WORKING → EXPLAIN → FEEDBACK이며 직접 설명 전 평가 요청을 차단한다.
- 직접 설명 시 새 흐름 화면에서 AI 패널을 닫고 기존 작업 API도 제출 상태로 잠근다. 외부 AI 사용을 차단하거나 본인 이해를 인증한 것으로 보지 않는다.
- 평가 입력은 250KB 이하로 제한하며 초과 시 제출을 실패로 반환하고 작업을 보존한다. 기록을 조용히 누락해 평가하지 않는다.

작업 AI와 별도 `learning-feedback-v1` 평가 프롬프트를 사용한다. 기존 `gemini-evaluation-v1` 및 다른 worktree의 미커밋 F05d v7을 변경하지 않는다. 기존 평가 예산(global/user)을 공유하고 작업당 최대 3회 명시 요청을 허용한다. 공급자 호출은 DB 트랜잭션 밖에서 실행한다. 제한된 실행기(동시 2/대기 8), 60초 공급자 timeout, 90초 stale 판정과 token CAS를 사용한다. 재시작 중 작업은 상태 조회 후 실패로 복구하며 성공 응답으로 대체하지 않는다.

평가기는 REQUEST/VERIFY/IMPROVE/EXPLAIN에 대해 관찰·보완점·다음 행동과 근거 ID를 반환한다. 화면에는 한국어 제목만 보여준다. 가장 먼저 해볼 다음 연습 한 영역을 지정한다. 서버가 선택된 근거 ID를 고정 원문으로 복원하므로 모델이 줄 범위와 인용문을 서로 다르게 작성하지 않는다. 미존재 ID·근거 없는 항목·추가 필드·중복 영역은 발행을 거부한다. **ID/구조 검증은 의미 정확성을 보장하지 않는다.** 원인 미확인을 반증으로 바꾸는 오류, 자기 보고를 실제 검증으로 단정하는 오류는 실제 응답 내용 검토가 필요하다.

재연습은 이전 결과물을 복사한 별도 훈련 작업에서 AI를 다시 사용한다. 이전 피드백과 원본 제출은 보존하며, 비교 화면은 이전/이번 결과물 및 검증 설명을 나란히 확인하게 한다. 변경 유무를 능력 향상 점수로 해석하지 않는다.

## 실행과 검증

현재 worktree는 `feature/P01-learning-flow`이며 origin/develop에서 분기한 후 검증된 I02 커밋을 의존성으로 cherry-pick했다. I02/F05d/원본 F00 작업 공간은 변경하지 않는다. PR·merge·배포는 이번 작업에서 수행하지 않는다.

```sh
npm install
cp .env.example .env  # 최초 설정에서만; 이미 설정한 .env를 덮어쓰지 않는다.
npm run db:up
npm run dev
```

기본 웹 포트는 3000이다. 현재 사용자 확인 환경은 `http://localhost:3189/learn`, API 8389, 기존 통합 PostgreSQL 55609의 `doezip_preview`로 고정한다. 최신 작업의 worktree에서 `.env`를 통해 이 환경에 연결하며 이전 worktree의 서버를 동시에 실행하지 않는다. Supabase의 기존 3189 callback 설정을 사용한다. 자동 검사는 별도 포트와 테스트 DB를 사용한다.

- `npm run check`: 계약/fixture/타입, web lint/typecheck/unit/build, JUnit/Testcontainers PostgreSQL, 실제 웹/API E2E. AI·OAuth는 가상 경계로 격리한다.
- `npm run test:learning:ai`: 실제 Gemini 4회, 가상 공개 입력만 사용. 기본 CI 제외. raw 후보는 apps/api/build/learning-quality 아래 보존한다. API 키는 루트 .env에서 명시적으로 읽고 로그에 출력하지 않는다.
- 최종 검사 결과와 실제 브라우저/AI 검토는 [검증 기록](P01_VALIDATION.md)에 별도 기록한다. 테스트 어댑터 성공과 실제 공급자 응답을 구분한다.

이 worktree의 확인 서버는 `doezip_preview` DB를 사용한다. 실행 중 재검사할 때에는 [검증 기록](P01_VALIDATION.md)의 별도 포트·테스트 DB 명령을 따른다.
