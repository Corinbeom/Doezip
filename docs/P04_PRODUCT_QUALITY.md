# P04 브라우저 기반 제품 품질 점검

## 점검 범위

2026-09-16 공개 데모 `https://doezip.vercel.app`에서 로그인 후 문제 탐색, 학습 목록, 완료된 보고서 과제 피드백, 완료된 구현 과제 피드백을 확인했다. 기능 성공 여부와 별도로 정보 위계, 용어, 이동, 긴 기록의 가독성을 점검했다.

## 확인한 문제와 조치

| 영향 | 확인한 문제 | 조치 |
|---|---|---|
| 높음 | 제품 화면의 브라우저 제목이 `Doezip 개발 환경 확인`으로 남아 있었다. | 제품명과 경로별 제목으로 교체했다. |
| 높음 | 상단 메뉴 세 항목이 모두 활성 상태처럼 밑줄 표시됐다. | 현재 경로 한 항목에만 `aria-current`와 활성 표시를 적용했다. |
| 높음 | 구현 피드백에 `PUBLIC_TEST`와 JSON 원문이 그대로 보였고, 보고서의 긴 원문·제출물이 핵심 피드백을 아래로 밀었다. | 사용자용 이름과 테스트 결과 문장으로 변환하고, 근거는 짧은 미리보기 뒤 펼쳐 보는 구조로 바꿨다. |
| 중간 | 완료한 과제가 기본 글머리표 목록이라 모드·단계·다음 행동을 빠르게 찾기 어려웠다. | 모드, 진행 단계, 과제 종류와 다음 행동을 분리한 기록 카드로 바꿨다. |
| 중간 | 제출 결과물, 검증 설명, 직접 설명의 위계가 약했고 검증 설명에는 제목이 없었다. | 세 기록을 구분한 읽기 전용 요약 영역으로 정리했다. |

## 전체 UI QA 후 추가 조치

Codex Desktop에서 실제 로그인 계정으로 보고서·구현 과제를 처음부터 AI 피드백까지 수행하고 1440×900, 768×900, 390×844, 320×700 화면을 확인했다. Blocker와 높은 우선순위 문제는 없었으며, 반복해서 확인된 중간 우선순위 문제를 다음과 같이 보완했다.

| 확인한 문제 | 조치 |
|---|---|
| 이어하기 목록에서 진행 중과 완료 기록, 마지막 작업 위치를 구분하기 어려웠다. | 두 그룹을 분리하고 완료 기록은 기본 접었다. 과제 안에서 마지막으로 본 이해·작업·검증 단계를 브라우저에 저장해 새로고침과 목록 카드에 반영한다. |
| 실패한 공개 테스트에 배열 JSON이 그대로 노출됐다. | 기존 저장 기록을 포함해 예상·실제 항목 수와 `id · title` 비교 문장으로 변환한다. |
| 모바일에서 힌트 세 개가 세로로 쌓여 작업 영역이 아래로 밀렸다. | 모바일 힌트를 짧은 3열 선택 탭과 선택한 행동 한 개로 압축했다. |
| 집중 피드백, 우선 연습, 전체 피드백과 근거 미리보기가 반복돼 화면이 길었다. | 전체 피드백은 기본 접고, 근거는 제목만 보인 뒤 펼쳤을 때 원문을 한 번 표시한다. |
| 모바일 터치 영역과 320px 코드 편집이 불편했다. | 주요 버튼과 이어하기 링크의 최소 높이를 44px로 맞추고, 코드 줄바꿈과 전체 화면 편집 모드를 추가했다. |

## 문제 콘텐츠 평가

현재 두 과제는 배포와 전체 흐름을 확인하는 입문 시나리오로는 사용할 수 있다. 실제 AI 활용 능력을 폭넓게 관찰하기에는 다음 한계가 있다.

- 보고서 과제는 한 개 자료의 다섯 시점만 비교하므로 출처 간 충돌, 우선순위 판단, 독자에 맞춘 의사결정을 충분히 관찰하기 어렵다.
- 구현 과제는 단일 `addItem` 함수와 모두 공개된 네 테스트로 구성되어 원인 탐색과 대안 비교가 짧게 끝난다.
- 훈련과 모의 전형의 차이가 안내·힌트 노출에 집중되어 과제 난도와 시간 압박, 제공 정보 범위의 차이가 작다.
- 과제 수가 보고서 1개, 구현 1개라 재연습이 같은 정답 구조를 반복하기 쉽다.

## 후속 콘텐츠 v0.2 기준

콘텐츠 변경은 기존 완료 기록을 보존하도록 새 과제·새 버전으로 추가한다. 적용한 migration이나 기존 시나리오를 덮어쓰지 않는다.

1. 보고서 과제는 서로 다른 2~3개 공개 자료, 일부 충돌하는 신호, 명확한 독자와 결정 시점을 포함한다.
2. 구현 과제는 재현 가능한 실패, 두 가지 이상 합리적 접근, 경계 입력과 회귀 검증을 포함한다.
3. 공개 테스트는 방향을 알려 주되 전체 해법을 노출하지 않고, 서버 검증을 도입하기 전까지 브라우저 보고라는 경계를 유지한다.
4. 평가는 정답 일치보다 요청의 구체성, AI 제안 비교, 실행 근거, 수정 이유와 남은 한계를 기록에서 관찰한다.
5. 훈련은 단계별 안내와 선택형 힌트를 제공하고, 모의 전형은 같은 역량을 새로운 자료와 제한된 안내로 관찰한다.

## 검증

- 공개 배포에서 수정 전 문제를 재현했다.
- Node.js 24.20.0과 격리된 PostgreSQL 컨테이너에서 `npm run check`를 실행했다.
- OpenAPI 스키마와 공개 fixture 31개, 웹 lint·typecheck·단위 테스트 101개·production build, API test·build가 통과했다.
- Playwright 브라우저 시나리오 49개가 통과했다. 변경된 피드백은 데스크톱과 375px 모바일 캡처로 정보 위계와 가로 넘침을 확인했다.
- 공개 배포 반영 전이므로 운영 환경의 변경 후 확인은 다음 배포에서 다시 수행한다.
